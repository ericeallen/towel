# Bug Handoff - Cross-File Import Path Generation Issue

**Date**: December 3, 2025
**Status**: CRITICAL - All PyPI versions yanked
**Affected Versions**: 1.0.3, 1.0.4 (and potentially earlier)

---

## Executive Summary

The towel refactoring tool has a critical bug in cross-file import path generation that makes it unusable for projects with `src/` layout. When extracting functions to different files, it generates incomplete module paths (e.g., `from ai.mcts import` instead of `from monte_chess.ai.mcts import`), causing `ModuleNotFoundError` at runtime.

---

## The Bug

### Symptoms

When running `towel dry` on a project with structure like:
```
monte_chess/
├── pyproject.toml  (with package-dir = {"": "src"})
└── src/
    └── monte_chess/
        ├── ai/
        │   └── mcts.py
        └── core/
            └── move_encoder.py
```

The generated imports are missing the top-level package name:
```python
# WRONG - generated by towel
from ai.mcts import __extracted_func_2

# CORRECT - should be
from monte_chess.ai.mcts import __extracted_func_2
```

### Reproduction

Confirmed reproducible on the `monte_chess` test codebase:
- User ran `towel dry src src_dry` from project root
- Generated code in `src_dry/` had broken imports
- After moving `src_dry/` to `src/`, tests fail with `ModuleNotFoundError: No module named 'ai'`

Multiple files affected in monte_chess:
- `src/monte_chess/core/move_encoder.py` - `from ai.mcts import`
- `src/monte_chess/gui/gui.py` - `from ai.self_play import`, `from cli.play import`, `from core.chess_env import`, `from cli.train import`

## Investigation Results

### Code Location

The bug is in **`src/towel/unification/refactor_engine.py`**, lines **2647-2688**:

```python
# Non-canonical file: insert import (module-level only)
if not proposal.insert_into_class:
    from_path = Path(proposal.file_path)
    to_path = Path(file_path)
    from pathlib import Path as _P

    common_dir = _P(
        __import__("os").path.commonpath([str(from_path), str(to_path)])
    )
    layout = ProjectLayout.discover(
        common_dir,
        prefer_absolute_imports=self.prefer_absolute_imports,
        pep420_namespace_packages=self.pep420_namespace_packages,
    )
    abs_mod = layout.module_name_for(from_path)  # <-- Returns wrong path
    if abs_mod and layout.prefer_absolute_imports:
        module_name = abs_mod
    else:
        if from_path.parent == to_path.parent:
            module_name = from_path.stem
        else:
            module_name = abs_mod or from_path.stem
    func_name = proposal.extracted_function.name
    import_line = f"from {module_name} import {func_name}\n"
```

### What Was Tested

1. **`ProjectLayout.module_name_for()` works correctly in isolation**:
   - Created test cases with various directory structures
   - Always returned correct full module paths (e.g., `monte_chess.ai.mcts`)
   - The `ProjectLayout` class itself is NOT the bug

2. **Path resolution appears correct**:
   - `module_name_for()` calls `file_path.resolve()` at line 153
   - Relative paths should be converted to absolute before processing
   - Source roots are discovered correctly from `pyproject.toml`

3. **Could not reproduce the exact bug in test cases**:
   - Created multiple test scenarios simulating the monte_chess structure
   - All tests returned correct module paths
   - Suggests the bug is context-dependent or timing-related

## Additional Issue: Circular Imports

Beyond the path bug, the monte_chess refactoring also created a **circular import** that would prevent the code from running even with correct paths:

```
monte_chess.ai.mcts
  → monte_chess.core.chess_env
  → monte_chess.core.move_encoder
  → monte_chess.ai.mcts  (tries to import __extracted_func_2)
```

This suggests the canonical file selection algorithm may need improvement to avoid creating dependency cycles.

## Hypotheses (Unconfirmed)

### Hypothesis 1: Working Directory Context
The bug may depend on the current working directory when `refactor_directory_to_fixed_point()` is called. If paths in proposals are stored as strings and later converted to `Path` objects, the resolution context might change.

### Hypothesis 2: In-Place Refactoring
When `input_dir == output_dir`, the refactoring happens in-place. The project layout discovery might behave differently when analyzing files that are being actively modified.

### Hypothesis 3: Proposal File Path Storage
The `proposal.file_path` might be stored as a relative path during the analysis phase, then resolved in a different working directory context during the application phase.

### Hypothesis 4: Fallback Logic Triggered
Lines 2680-2683 in refactor_engine.py have fallback logic:
```python
if from_path.parent == to_path.parent:
    module_name = from_path.stem
else:
    module_name = abs_mod or from_path.stem
```

If `abs_mod` is somehow `None`, this would fall back to `from_path.stem`, which could explain partial paths. However, the user reports paths like `"ai.mcts"` not just `"mcts"`, so this doesn't fully explain it.
